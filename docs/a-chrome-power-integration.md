2026-11-19: 운영 서버에 Chrome 이벤트 중계만 배포했다. server/main.py의 지원 플래그와 server/contracts.py의 세 종류 검증만 교체했고 B/C 및 인증정보 해시는 유지됐다. 기존 A 파일 백업: `/home/ubuntu/cloudnet-backups/chrome-timeline-20261119T062718Z`. TLS 관리자 등록에서 `exam_chrome_timeline_v1: true`를 확인했다. 동일 조건의 로컬 TLS Agent 테스트에서 세 이벤트의 중계·저장·중복 제거를 확인했다. 배포 이후 PC-01/02/03 재등록 로그를 확인했으나 실제 Chrome 탭 조작과 C 표시의 공동 검증은 남아 있다. 서버 재시작으로 시험 상태는 재확인이 필요하며 A가 자동으로 시험을 시작하지 않았다.

전원 제어는 **운영 서버에 배포**했고 2026-11-19 06:46 UTC TLS 관리자 등록에서 `power_control_v1:true`를 확인했다. 서버는 TLS와 인증 및 감사 DB가 있는 연결에서 플래그를 알리고, Agent 등록의 `boot_id`와 `power_control_mode`를 검증·노출한다. 관리자 요청의 대상·인증·유효기간·모드·부팅 ID를 검증하고 DB에 중복 방지 예약을 기록한 다음 두 고정 동작만 중계한다. 접수는 비최종 결과로 중계하고 최종 응답을 위한 시간을 추가한다. 결과를 감사 DB에 기록하고, 실행 모드의 재부팅 요청 이후 5분 내 새 부팅 ID가 관찰되면 확인 시각과 ID를 기록한다. 이것은 부팅 ID의 변화를 관찰한 결과다. 종료의 실제 전원 상태는 PC 소유자의 확인이 필요하다.

기존 감사 DB에 확인용 열을 추가한다. 기존 감사 이력과 인증정보를 보존한다. 로컬 테스트에서 B의 `simulate` 모드로 TLS를 통해 요청·접수·최종 응답과 중복 거절을 확인했으며 실제 Windows 전원 명령을 실행하지 않았다. 서버 관련 66개 테스트가 통과했다.

운영 적용은 A의 4주차 변경과 함께 했으며 코드와 DB 백업은 `/home/ubuntu/cloudnet-backups/week3-20261119T064636Z`에 보존했다. B·C와 모의 모드로 먼저 공동 검증한다. 실제 종료·재부팅은 해당 테스트 PC와 소유자 승인을 별도로 확인한다. 인증 실패·모드 또는 부팅 ID 불일치·DB 오류는 명령을 전달하지 않는다. 실제 기기의 전원 동작과 GUI 전체 경로는 아직 검증하지 않았다.
