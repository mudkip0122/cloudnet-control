# A→C 시험 이벤트·상태·RTT 합의 — C 반영

기준: A `ef3f64e`, B `57b530b`. 사용자가 전달한 A 제안에 C가 동의했고 아래 규격으로 C를 구현했습니다. A의 실제 구독 중계와 지원 플래그 구현 완료를 뜻하지 않습니다.

후속: A c5ecfef에 기존 구독·상태 중계가 구현됐고 C는 별도 연결의 subscribe_exam:true와 subscribe_status:true를 함께 사용합니다. 최신 A 필드는 [A 확정 규격](a-c-exam-contract.md)을, 이후 B가 추가한 Chrome 전경 감시는 [C 전경 감시 인계](c-foreground-handoff.md)를 따릅니다. 아래 ef3f64e 미구현 표기는 당시 기준입니다.

## 합의 내용

1. 기존 GUI의 LIST_DEVICES 1초 폴링을 유지합니다. 별도 TLS 관리자 연결에서 기존 관리자 토큰으로 REGISTER에 `subscribe_exam:true`를 넣고 원문 `EXAM_EVENT`를 수신합니다. 기존 폴링 연결에 시험 이벤트를 섞지 않습니다. 새로운 이벤트 ACK는 추가하지 않습니다.
2. 현재 `exam_mode`는 DEVICE_LIST의 각 PC와 STATUS_UPDATE의 device에 B COMMAND_RESULT와 같은 구조로 포함합니다. 모드 변경 성공·MONITOR_STATUS·새 Agent 등록·단절 시 A가 현재 상태를 갱신하고, 새 연결/단절의 상태는 null로 무효화합니다. C는 다른 관리자 변경도 이 필드로 동기화하며 감지 이력만으로 켜짐이나 현재 실행을 추정하지 않습니다.
3. RTT는 기존 `rtt_ms`, `rtt_status`, `rtt_timestamp`를 유지합니다. A의 `metrics_stale`은 측정값 수신 후 6초 초과 여부를 서버 단조 시계로 판정한 boolean입니다. C는 `metrics_stale:false`가 확인되고 Agent 시각·상태도 유효할 때만 RTT를 표시합니다. Heartbeat의 last_received를 RTT 신선도 근거로 사용하지 않습니다. `last_metrics_received`를 서버 측정 수신 UTC로 표시합니다.
4. PC 시계 오차가 큰 경우 C는 보수적으로 수치를 숨깁니다. 기존 표시 기준은 METRICS -6~6초, RTT -6~8초이며 METRICS 수신으로 이전 RTT 측정 시각을 갱신하지 않습니다.
5. 현 단계의 공통 관리자 토큰 사용자는 동일 감독 역할로 취급합니다. 개인별 신원이나 시험별 권한 분리를 구현했다고 표현하지 않습니다. 해당 분리가 필요하면 별도 인증 설계를 합의합니다.

## C 구현

- 구독 연결은 LIST_DEVICES를 주기적으로 보내 활동을 유지하며, 응답 사이 EXAM_EVENT/STATUS_UPDATE를 수신합니다. 상태 전체 목록은 기존 폴링에서도 수신하므로 시험 구독 장애가 일반 모니터링을 중단시키지 않습니다.
- 이벤트는 메트릭 최신값 큐와 분리된 최대 2048개 FIFO로 전달하고 Tk 메인 스레드에서 처리합니다. 한 tick에 최대 200개를 처리합니다. 포화 시 조용히 덮어쓰지 않고 연결을 종료·재시도하며 이력 공백 가능성을 표시합니다. 이는 서버의 저장 이벤트 재전송이나 무손실 보장을 뜻하지 않습니다.
- 최근 4096개 event_id를 기억해 중복 경고를 억제합니다. 현재 GUI 세션의 감지·감시 상태 이력은 최근 500개로 제한합니다. 이벤트 저장소는 A 소유이며 서버 과거 이력 조회는 별도 범위입니다.
- 모든 PC의 PC ID·시험 ID·프로그램·PID·이벤트 시각을 시험 모드 창에 표시하고, 메인 화면에 마지막 감지 경고를 표시합니다. ‘현재 실행 중’이나 ‘부정행위 확정’으로 표현하지 않습니다. 단절·모드 끄기·PC 전환 뒤에도 감지 이력은 유지합니다.
- 현재 시험 상태는 서버 스냅샷 기준으로 starting/ok/partial/unavailable/off/미확인/연결 끊김을 구분합니다. 다른 관리자의 끄기와 재접속 무효화도 반영합니다. 감시 이벤트 자체도 이력에 표시합니다.
- 명령 성공 전에는 켜짐/꺼짐을 확정하지 않고, 명령·PC ID·code·exam_mode를 검증합니다. 연결/대상 변경 뒤에는 GET_EXAM_STATUS로 다시 확인하며 켜기/끄기/종료를 자동 재전송하지 않습니다. 오프라인에서도 감지 이력 열람은 허용하고 제어 버튼은 비활성화합니다.
- 이벤트가 없거나 관리자 등록이 성공했다는 이유만으로 시험 이벤트 중계 지원·정상 감시·시험 준수를 확정하지 않습니다. A `ef3f64e`는 subscribe_exam 중계가 없으므로 관리자 연결이 되어도 이벤트가 도착하지 않을 수 있습니다.

## A에 필요한 후속 작업

합의된 subscribe_exam 구독과 원문 이벤트 중계, exam_mode 스냅샷/상태 변경 반영, Agent 시험 지원 플래그를 A에서 구현해야 합니다. 기존 ef3f64e 코드는 시험 이벤트 저장까지만 수행하므로 실제 A→C 시험 연동 완료로 표시하지 않습니다. B 기본 금지 목록을 쓰기 위해 forbidden_processes를 생략하는 입력은 A에서 아직 허용하지 않으므로 현재 C는 명시적인 목록을 보내 호환성을 유지합니다.

이후 A·B·C가 실제 TLS 모드 켜기→감지→중복 억제→끄기→다른 관리자 상태 동기화→단절/재접속→RTT 지연을 공동 검증합니다. main 병합·운영 배포는 공동 검증 후에 진행합니다.

## C 검증 결과

전체 테스트 172개 통과. 새 시험 구독의 모의 소켓 서버 검증은 등록 subscribe_exam:true, 연속 이벤트 80개와 STATUS_UPDATE/DEVICE_LIST 혼합 수신, 인증 거절 시 중단, 큐 포화 시 명시적 오류를 확인합니다. 실제 Tk 위젯에서 중복 경고 억제·감지 이력·다른 관리자 끄기 상태 반영·단절 후 이력 유지와 열람을 확인합니다. 기존 실제 GUI→TLS 서버→Agent 프로세스 흐름과 샘플 대시보드도 통과했습니다. 신규 시험 구독을 실제 A 서버에서 검증한 결과는 아닙니다.
