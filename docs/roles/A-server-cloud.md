# A 담당 — 서버·클라우드

담당자: 미정

## 담당 목표와 범위

Windows Agent와 관리자 GUI 사이에서 인증된 메시지를 중계하고, PC 3대가 동시에 연결되는 EC2 서버를 완성합니다. 주 작업 경로는 `server/`이며, `common/` 통신 규격 초안과 배포 문서도 담당합니다.

이 문서는 작업 배정안입니다. 아래 체크박스는 구현 완료를 의미하지 않습니다. 전체 일정은 [프로젝트 계획서](../project-plan.md)를 따릅니다.

## 먼저 할 일

1. B·C와 사용할 Python 버전 및 로컬 실행 방법을 확정합니다.
2. `docs/protocol.md` 초안을 작성하고 B·C에게 검토받습니다.
3. 공통 송수신 코드와 로컬 서버를 만들어 Agent 한 대의 등록·측정값 수신을 확인합니다.
4. C에게 PC 목록과 측정값을 전달해 첫 통합을 진행합니다.
5. TLS·인증을 적용하고 EC2에서 같은 흐름을 확인합니다.

## 주차별 작업과 완료 기준

### 1주 차: 규격과 개발·배포 환경

- [ ] JSON 인코딩, 4바이트 길이 헤더의 바이트 순서, 최대 크기, 필수 필드와 오류 응답 정의
- [ ] 등록·인증 응답, PC 목록, 이력 조회 등 기존 메시지 목록에서 빠진 흐름을 B·C와 확정
- [ ] Agent/Admin 자격증명과 권한 범위, Agent ID에 대한 인증정보 매핑 방식 정의
- [ ] EC2 Ubuntu 개발 환경, TLS 인증서 준비 및 클라이언트 검증 방법 문서화
- [ ] 서비스 포트·SSH 접근 범위 제한, 비용 알림 및 자원 정리 절차 준비
- [ ] `common/`의 송수신·검증 기능 인터페이스를 B·C와 합의

**산출물:** `docs/protocol.md`, 서버 실행 안내, EC2 구축 기록. 비밀값과 개인키는 제외합니다.

**완료 기준:** 로컬 PC에서 EC2 테스트 서버로 연결해 메시지 왕복을 확인하고, B·C가 동일한 규격을 설명할 수 있습니다.

### 2주 차: 다중 연결과 인증

- [ ] TLS 서버의 연결 수신과 연결별 처리 구현
- [ ] 분할 수신·연속 메시지를 처리하는 정확한 길이 기반 송수신 구현
- [ ] 미인증 메시지 거절, 역할별 요청 제한, 잘못된 JSON·과대 메시지 처리
- [ ] 세션 등록·해제, 중복 Agent ID 정책, 공유 세션 자료구조 동기화 구현
- [ ] 한 연결에 여러 스레드가 전송할 때 메시지가 섞이지 않도록 직렬화
- [ ] Heartbeat 만료 감지와 관리자 PC 목록·상태 변경 중계 구현

**완료 기준:** Agent 3대와 GUI가 연결되고, 한 Agent의 비정상 종료가 나머지 연결에 영향을 주지 않습니다.

### 3주 차: 측정값 중계

- [ ] 인증된 Agent의 측정값만 수신하고 발신 세션과 PC ID 일치 여부 검사
- [ ] CPU·RAM 범위, 네트워크 단위, 타임스탬프 유효성 검사
- [ ] 관리자에게 PC별 최신값과 갱신 시각 전달
- [ ] 느린 관리자 연결이 다른 PC의 수집을 막지 않도록 처리
- [ ] C와 수신 지연·오래된 데이터의 표시 기준 확정

**완료 기준:** PC 3대의 측정값이 섞이지 않고 GUI에 전달되며, 부하 변화가 반영됩니다.

### 4주 차: 저장·이력·경고

- [ ] C와 `devices`, `metrics`, `events`, `commands` 스키마 및 ERD 검토
- [ ] 서버 측 SQLite 초기화·쓰기·조회 모듈 구현 및 동시 접근 처리
- [ ] 기간·PC별 이력 요청 검증과 조회 결과 응답 구현
- [ ] 보관 기간, 조회 결과 크기 제한, DB 오류 처리 구현
- [ ] 서버에서 오프라인 이벤트와 CPU·RAM 임계치 경고 판정·기록
- [ ] 지속 시간, 중복 억제, 정상 복귀 기준을 C와 합의

**완료 기준:** 서버 재시작 후에도 이력을 조회하고, 연결 끊김과 임계치 경고가 기록됩니다.

### 5주 차: 원격 명령 검증과 중계

- [ ] 관리자 권한, 대상 연결 상태, 허용 동작을 검증
- [ ] 명령 ID·대상·실행자·생성 시각·만료 시각을 기록하고 중복 요청 처리
- [ ] B에게 검증된 명령만 전달하고 결과를 요청한 관리자에게 중계
- [ ] 접수·실행 시작·실패·시간 초과를 구분해 기록
- [ ] 재연결 후 부팅 식별값 변화로 재부팅 성공 여부 확인

**완료 기준:** 미인증·중복·만료 요청이 거절되고, 승인된 재부팅의 요청부터 재접속까지 감사 기록이 남습니다.

### 6주 차: 안정화와 발표

- [ ] PC 3대의 30분 연속 통합 테스트 주관
- [ ] 서버 재시작·잘못된 인증·DB 오류·연결 단절 시나리오 확인
- [ ] 설치·실행·중지·복구 문서와 배포 설정 예시 작성
- [ ] 구성도, 인증 흐름, 장애 해결 사례 발표 자료 제공

**완료 기준:** 다른 팀원이 문서만 보고 서버를 실행하고 통합 시연을 재현합니다.

## 협업 경계

| 상대 | A가 제공할 것 | 상대에게 받을 것 |
|---|---|---|
| B | 서버 주소·포트, 인증·TLS 안내, 공통 송수신 규격 | 등록 정보, 측정값, Heartbeat, 명령 결과, 부팅 식별값 |
| C | PC 목록·상태·측정값·이력·경고·명령 결과 응답 | 화면에 필요한 필드, 조회 조건, 관리자 명령 요청 |

SQLite는 서버만 접근합니다. C는 조회 요구사항과 스키마 설계에 참여하며 GUI는 TCP/TLS 요청으로 이력을 받습니다. GUI에서 EC2의 DB 파일을 직접 열지 않습니다.

`common/` 변경은 A가 초안을 작성하고 B·C가 호환성을 검토합니다. 등록 응답과 이력 조회 등의 메시지 이름은 프로토콜 문서에서 확정합니다.
