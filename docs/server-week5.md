# A 5주차: 원격 명령 검증과 감사

2026-11-19 06:57 UTC: A 서버 `129d919`를 EC2에 배포했다. 기존 코드·SQLite 백업은 `/home/ubuntu/cloudnet-backups/week3-20261119T065746Z`에 보존했고 B/C와 인증 파일 변경이 없음을 확인했다. TLS 등록에서 이력·전원·시험 이벤트·카메라 기능 지원을 확인했다. 재시작 후 실제 PC-01/02/03이 재연결되어 측정값이 갱신됐고 최근 이력은 각각 296건씩 읽혔다. 이는 서버 측 읽기 검증이며 C GUI나 실제 전원 동작 검증은 아니다.

## 구현 범위

TLS와 공통 관리자 토큰으로 관리자 연결을 인증한다. Agent는 각 PC 토큰으로 별도 인증한다. Windows 사용자 비밀번호는 수집하지 않는다. 공통 관리자 토큰은 모든 PC에 권한이 있으며 실행자의 `executor`는 연결 단위 식별자다. 개별 사람을 구분해 감사하는 계정 체계는 구현되지 않았고 A·C 합의가 필요하다.

인증된 관리자 요청은 대상 연결, 만료 시각, 허용된 명령을 검증한다. 프로세스 조회·종료와 PC 종료·재부팅은 별도의 action이며 `shell`, `command`, `cmd`, `args` 필드를 거절한다. 종료할 프로세스의 PID·생성 시각은 Agent에 그대로 보내고 보호 판정은 Agent가 수행한다. 전원 명령은 해당 Agent의 `power_control_mode`와 `boot_id`가 요청과 일치해야 하며 감사 DB를 사용할 수 있어야 전달한다. 실제 Windows 종료 명령을 서버에서 직접 실행하지 않는다.

서버는 전달 전 고유 명령 ID를 SQLite에 예약하며 요청·대상·연결 식별자·수신 시각·만료 시각을 기록한다. 30일 보관 중인 명령 ID는 서버나 Agent 재시작 후에도 다시 실행하지 않는다. `command_transitions`는 접수, Agent의 중간·최종 결과 코드, 시간 초과, 전달 결과 미확인, 서버 재시작으로 인한 결과 미확인, 부팅 ID 변화 확인을 순서대로 기록한다. 응답이 없으면 `COMMAND_TIMEOUT`으로 표시하며 자동 재전송하지 않는다. 전송 중 오류는 실제 전달 여부가 불확실하다. Agent의 `POWER_ACCEPTED` 이후 최종 응답을 위한 시간을 추가한다.

실행 모드 재부팅 명령의 접수 또는 실행 시작·미확인 결과 이후 5분 내 같은 PC가 새 부팅 시각으로 등록하면, 이전 부팅 시각보다 늦고 요청 시각보다 이전이 아닌 경우에만 관측 시각과 부팅 ID를 기록한다. 이는 부팅 변화 관찰이며 실제 원인이나 PC 종료 상태를 독립적으로 증명하지 않는다. 같은 기간에 별도의 수동 재부팅이 있었다면 명령으로 인한 재부팅과 구분할 수 없다.

## 검증과 남은 공동 확인

로컬 TLS 환경에서 B Agent의 `simulate` 모드로 서버 인증·모드/부팅 ID 검증·요청 전달·접수와 최종 결과·중복 거절을 확인했다. 시간 초과와 접수 후 시간 초과의 감사 순서, 이전 부팅 시각 재사용 거절도 자동 테스트한다. 실제 PC 전원 명령은 실행하지 않았다. 실제 대상 PC와 소유자 승인, B Agent 실행 모드, C 확인창·단계별 표시·재연결 결과는 함께 확인해야 한다.

관련 서버·프로토콜·B 모의 전원 테스트 79개가 통과했다. 이력·카메라·전원 지원의 이전 배포는 [4주차 결과](server-week4.md), [Chrome·전원 연동](a-chrome-power-integration.md), [카메라 구독 계약](a-camera-stream-contract.md)을 참고한다. 영상 구독은 C의 최신 화면과 연결 규격 합의가 별도로 남아 있다.
